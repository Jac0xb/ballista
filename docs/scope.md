# Ballista 0.3 scope and limits

## Product statement

Ballista turns a bounded orchestration template into an immutable, publicly reusable on-chain
primitive. It is not an automation network, custody layer, or general-purpose programming language.

That distinction keeps the value proposition legible: less repeated instruction construction,
consistent validation, and a small execution surface that can be measured in compute units.

## Deliberate scope cuts

| Earlier experiment | 0.3 decision | Reason |
| --- | --- | --- |
| Recursive command AST | Flat record tables | Supports borrowed parsing and exact bounds |
| Unbounded or nested loops | One inferred tail-account range | Preserves batching while guaranteeing termination |
| Mutable caches or instances | SSA-like registers per run | Keeps templates immutable and execution stateless |
| Bespoke protocol evaluators | SDK helpers compiling to generic CPI | Keeps the runtime protocol-neutral |
| Ballista-controlled PDA signers | Outer transaction signers only | Avoids custody and hidden authority |
| Scheduler and keeper rules | Out of scope | Authorization and replay remain explicit downstream concerns |
| Generated clients as product API | Zod authoring plus shared codecs | Gives named bindings and actionable errors before transaction construction |

## Zero-copy boundary

The account header and all fixed-size bytecode records are alignment-free Zerocopy types. Section
lengths are derived from the program header and must consume the payload exactly; there are no owned
`Vec`, `String`, or `Box` values on the run parsing path. Runtime registers hold calculated values
and bounded byte slices, while CPI metas and generated instruction bytes are necessarily assembled
for invocation.

Finalization performs the expensive structural and type verification once. A run checks the account
envelope, input encoding, account bindings, and execution safety, but does not hash or revalidate the
entire immutable bytecode.

## Hard limits

| Resource | Limit |
| --- | ---: |
| Compiled template payload | 10,240 bytes |
| Runtime account slots | 60 |
| Typed inputs / encoded input bytes | 32 / 1,024 |
| Runtime registers / VM records | 64 / 128 |
| Expanded CPIs | 64 |
| Generated bytes per CPI | 4,096 |
| Batch row stride | 1 to 8 accounts |

The iterator count is inferred from the tail-account count, must divide evenly by its stride, and
cannot exceed the template maximum. Transaction account locks, compute, instruction restrictions,
and packet size can impose lower practical limits.

## Dependency policy

- Application-facing dependencies are exact-pinned in the JS package and recorded in
  `pnpm-lock.yaml`.
- Dependency build scripts are denied by default; only `esbuild` is explicitly allowlisted.
- Rust wire-format upgrades include exact byte fixtures in both Rust and TypeScript.
- Runtime crates are exact-pinned around Pinocchio 0.11 and verified with `cargo build-sbf`.

## Product boundary for use cases

The [use-case matrix](../usecases.md) says what the language can express when a suitable downstream
instruction and authority model already exist. It does not mean Ballista can invent a protocol
operation, source a swap route, keep oracle data fresh, sign for a user, or execute itself later.
