# Limits

| Resource | Hard limit |
| --- | ---: |
| Compiled template payload | 10,240 bytes |
| Runtime account slots | 120 |
| Typed inputs, fixed plus row | 32 |
| Row inputs per batch row | 0 to 8 |
| Input values per run (fixed plus rows) | 256 |
| Encoded input bytes | 1,024 |
| Account groups | 8, up to 255 members each |
| Runtime registers | 64 |
| VM instruction records | 128 |
| Expanded CPIs | 64 |
| Accounts per CPI | 64 |
| Generated bytes per CPI | 4,096 |
| Batch row stride | 1 to 8 accounts |
| Batch minimum iterations | 0 to the maximum |
| Caller-provided PDA seeds | 15 |
| Bytes per PDA seed | 32 |
| Readable return data | 1,024 bytes |

## Static versus runtime

Compilation and finalization reject structural maxima: register count, instruction count, CPI
expansion, CPI account counts, seed bounds, worst-case generated bytes, fixed-offset reads past the
declared minimum data length, and carried registers that change type. `Run` checks actual inputs,
row count against both bounds, account group sizes against the accounts supplied, account
privileges, owners, addresses, and data lengths. A CPI's declared accounts plus its forwarded group
must fit 64 accounts, checked at run time.

## Heap

A run allocates its register file and one set of CPI scratch buffers, then reuses them for every
invocation. PDA seeds are assembled on the stack. Heap use is therefore constant per run and stays
well inside the default 32 KiB frame even at 64 CPIs carrying 4 KiB each.

## Transaction ceilings

Transaction v1 allows 4,096 serialized bytes and 64 inline account addresses. Ballista reserves at
most 120 runtime slots; the template, Ballista program, payer, and downstream program IDs still
count toward the transaction-wide account limit when unique. Runs with more than about 60 accounts
need an address lookup table.

Compute remains workload-specific. PDA bump searches, raw data reads, CPIs, and downstream program
logic all contribute. Simulate the exact message and apply measured resource limits with headroom.

## When to split a workflow

Split or redesign when the template approaches multiple ceilings simultaneously. Favor several
small public templates over one opaque "do everything" artifact, especially when independent steps
do not require atomicity.
