# Limits

| Resource | Hard limit |
| --- | ---: |
| Compiled template payload | 10,240 bytes |
| Runtime account slots | 60 |
| Typed inputs | 32 |
| Encoded input bytes | 1,024 |
| Runtime registers | 64 |
| VM instruction records | 128 |
| Expanded CPIs | 64 |
| Generated bytes per CPI | 4,096 |
| Batch row stride | 1 to 8 accounts |
| Caller-provided PDA seeds | 15 |
| Bytes per PDA seed | 32 |

## Static versus runtime

Compilation and finalization reject structural maxima: register count, instruction count, CPI
expansion, seed bounds, and worst-case generated bytes. `Run` checks actual inputs, row count,
account privileges, owners, addresses, and data lengths.

## Transaction ceilings

Transaction v1 allows 4,096 serialized bytes and 64 inline account addresses. Ballista reserves at
most 60 runtime slots; the template, Ballista program, payer, and downstream program IDs still count
toward the transaction-wide account limit when unique.

Compute remains workload-specific. PDA bump searches, raw data reads, CPIs, and downstream program
logic all contribute. Simulate the exact message and apply measured resource limits with headroom.

## When to split a workflow

Split or redesign when the template approaches multiple ceilings simultaneously. Favor several
small public templates over one opaque “do everything” artifact, especially when independent steps
do not require atomicity.
